# B11.74 - Deterministic native database closure

Status: active. Owner: memory-nexus. Discovered during B11.4 at 0423e45.

The end state is a closed connection whose owned statements no longer retain
native database handles. Cleanup must not depend on the next test, garbage
collection, an unbounded wait or process exit. Preserve storage ownership,
committed data, rollback behavior and useful errors.

## Verified starting evidence

- The ordinary seven-file JSON test group failed with EBUSY after an experimental
  three-attempt / 100+200ms retry policy. Five instrumented six-file repetitions
  passed; those passes do not invalidate the ordinary-suite failure.
- A retained prepared statement stays usable after `Database.close()` on actual
  Windows Bun 1.4.1 and 1.3.14, and immediate file removal fails with EBUSY.
- `close(true)` finalizes/releases in 1.4.1 but throws `database is locked` in
  1.3.14. Explicit statement finalization before close releases the file in both.
- The 1.3.14 runtime was downloaded from its official GitHub release, matched
  the release SHA-256, ran only the synthetic probe, and was removed afterward.
  This is Windows compatibility evidence, not Linux execution.
- Initial source search finds 67 source/test/script files referencing
  `closeDatabase` and 76 `prepare` call lines in repository adapters. These are
  discovery counts, not a complete caller/lifetime audit.
- Shared `closeDatabase` calls default `db.close()`. SqliteLinkRepository has
  three retained prepared fields and another prepared traversal statement.
  Its ownership/finalization is not explicit. The mechanism is proven; the
  primitive probe alone does not establish every individual command's cause.

Evidence: `evidence/B11.4-native-discovery.json`. The rejected retry source,
successful and failed runs, native probes and pinned-source references survive
there. The retry implementation was removed; no runtime floor was changed.

## Atomic execution order

1. Reproduce the retained-statement problem through actual `closeDatabase`, in
   an owned synthetic fixture. Keep the statement strongly referenced so the
   regression does not accidentally pass through GC. Prove normal closure,
   repeated closure, failure reporting and immediate safe removal.
2. Map the production connection factories, statement creation, transaction
   ownership, queries/iterators and external database callers. Read their
   interfaces before selecting the lifecycle boundary. Derive the minimum
   ownership structure before comparing implementation options.
3. Choose the smallest design that reliably finalizes owned statements. Do not
   simply substitute `close(true)` across the supported range, blindly replace
   every prepare with query, or add a global strong-reference registry that
   retains one-off statements indefinitely. Evaluate explicit disposal at
   adapter scope versus connection-owned lifetime. A runtime-floor change must
   be an explicit D02/D03 compatibility disposition, not a hidden shortcut.
4. Implement a focused vertical slice using RED/GREEN tests, then wire all
   affected owners/callers. Verify committed data and unfinished-transaction
   rollback, statement failure, repeated close, concurrent independent databases
   and resource release. Keep the declared runtime contract honest: the current
   `bun >=1.0.0` claim is broader than the two runtimes verified here.
5. Run the actual JSON command suites and affected connection/helper/adapter
   checks under owned outer storage. Re-run the previously failing native path
   with retained statement references; use bounded repetition only as additional
   evidence. Rebaseline affected B11.1/B11.4 evidence, per-file Tier S decisions,
   native platform results and independent review. Do not carry earlier metric
   or review acceptance to changed source.
