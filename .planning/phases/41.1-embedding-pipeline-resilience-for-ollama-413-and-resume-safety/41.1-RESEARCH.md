# Phase 41.1: Embedding Pipeline Resilience - Research

## Problem Model

The current failure is a deterministic processing deadlock:

1. `findUnembedded(batchSize)` selects the same first unembedded rows.
2. `EmbeddingService` sends the whole set to the provider.
3. Ollama/nginx returns 413 for an oversized request.
4. No embeddings are stored for that batch.
5. The next run selects the same rows and fails again.

This is not a Tailscale routing problem. The live endpoint responded successfully. It is not solved robustly by lowering `batchSize` because message sizes vary and other providers/transports can impose different request-size ceilings.

## Design Principles

### 1. Monotonic Progress

Each embedding pass must either:
- persist embeddings,
- persist a durable safe skip/quarantine for non-retryable single-item failures,
- or fail with a retryable/systemic error that has not silently changed corpus state.

It must not repeatedly hit the same deterministic non-retryable request.

### 2. Provider-Agnostic Application Contract

The application layer should react to a typed `payload_too_large` category rather than string-matching Ollama or nginx messages. The Ollama adapter should translate HTTP 413 into that typed category.

### 3. Adaptive Split Before Quarantine

Multi-item oversized batches are still valid work. The correct response is deterministic split and retry, preserving input/result order.

Single-item oversized failures cannot be solved by splitting the batch. They should be model-scoped skipped/quarantined with privacy-safe metadata.

### 4. Privacy-Safe Failure Records

Skip/quarantine records may include:
- message id
- model hash
- provider id
- model name
- reason code
- retryable boolean
- content byte count
- content hash/fingerprint
- timestamp

They must not include raw message text, raw transcript fragments, prompt text, or provider request bodies.

### 5. Model-Scoped Resume

Skip state must be scoped to the embedding model hash. A future model or embedding config should not be blocked by old skip records created for another model.

## Recommended Implementation

1. Add typed provider error support in `src/domain/ports/embedding.ts`.
2. Teach `OllamaEmbeddingProvider.embedBatch` to split and retry on HTTP 413 for multi-item batches.
3. Add optional `maxBatchBytes` to embedding config with a conservative default.
4. Add byte-bounded application sub-batching so normal operation avoids large provider payloads before hitting a 413.
5. Add durable skip/quarantine state in SQLite and repository ports.
6. Update `findUnembedded` to exclude current-model skipped messages.
7. Update embedding pass results and CLI output to include skipped counts and safe reasons.

## Validation Architecture

Tests must prove the following without reaching a real provider:

- A mocked Ollama 413 on a multi-item batch causes split calls and returns embeddings in original order.
- A mocked Ollama 413 on a single item throws a typed payload-too-large error and does not expose raw text.
- Application batching respects `maxBatchBytes` even when `batchSize` would allow more items.
- A single oversized message is marked skipped and a later message in the same pass can still embed.
- `findUnembedded(limit, modelHash)` excludes current-model skipped rows but not old-model skipped rows.
- CLI sync output reports skipped rows without raw message content.
