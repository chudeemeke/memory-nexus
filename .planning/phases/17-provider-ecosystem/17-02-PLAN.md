# Plan 17-02: Dimension-Aware Re-embedding on Provider/Model Change

## Goal

When the user switches providers or models (e.g., local 384d to OpenAI 1536d), the vec0 table must be dropped and recreated with the new dimension before re-embedding. The existing `clearAllEmbeddings()` only DELETEs rows -- it does not change the structural dimension of the vec0 table. This plan adds dimension-aware vec0 table recreation and integrates it into the re-embedding flow.

## Context

The existing re-embedding flow in `sync.ts` `runEmbeddingPass()`:
1. `EmbeddingService.checkModelState()` detects model hash change
2. `handleModelChange()` prompts user for confirmation
3. `service.clearAndReembed()` calls `repository.clearAllEmbeddings()` (DELETE FROM) then `embedUnembedded()`

The gap: `clearAllEmbeddings()` only DELETEs rows. The vec0 virtual table `message_embeddings` was created with `float[384]` in schema.ts. Inserting a 1536-dimensional Float32Array into a `float[384]` table causes sqlite-vec errors.

**Solution:** Add `recreateVecTable(dimensions)` to `EmbeddingRepository`. Call it during the re-embedding flow when dimensions differ between stored and configured. The `MESSAGE_EMBEDDINGS_TABLE` constant in schema.ts is parameterized at creation time only -- at runtime, we DROP and CREATE with the new dimension via inline SQL (schema.ts is not modified).

## must_haves

- `EmbeddingRepository.recreateVecTable(dimensions)` drops and recreates message_embeddings with the specified dimension
- `EmbeddingRepository.getStoredEmbeddingDimensions()` returns the dimension of currently stored embeddings (or null if none)
- Re-embedding flow in sync.ts detects dimension change and calls `recreateVecTable()` before `clearAndReembed()`
- Existing 384d -> 384d model changes (same dimension) still use DELETE-only path (no table recreation)
- Cross-dimension switches (384d -> 1536d, 1536d -> 768d) work correctly
- All tests pass with 95%+ coverage at each metric for new and modified code

### Task 1: Dimension-aware vec0 table operations in EmbeddingRepository (RED-GREEN)

Add methods to the repository for inspecting and recreating the vec0 table with new dimensions.

#### EmbeddingRepository extension (`src/infrastructure/database/repositories/embedding-repository.ts`)

**Test file:** `src/infrastructure/database/repositories/embedding-repository.test.ts`

Tests to write (RED phase):

**getStoredEmbeddingDimensions():**
1. Returns null when message_embeddings table has no rows
2. Returns the dimension of stored embeddings (e.g., 384) by querying an actual stored vector
3. Returns correct dimension after storing 1536d embeddings

Strategy for detecting stored dimensions: Query a single embedding from message_embeddings and check the Float32Array length. The vec0 table stores raw vectors -- reading one back reveals its dimension. Alternative: probe the vec0 table definition via `PRAGMA table_info` (but vec0 virtual tables may not report this reliably). Safest approach: query one row, check the length of the returned embedding vector.

Implementation:
```typescript
getStoredEmbeddingDimensions(): number | null {
  // Check if any embeddings exist
  const countRow = this.db.prepare<{ count: number }, []>(
    "SELECT COUNT(*) as count FROM message_embeddings"
  ).get();
  if (!countRow || countRow.count === 0) return null;

  // Fetch one embedding to check its length
  const row = this.db.prepare<{ embedding: Uint8Array }, []>(
    "SELECT embedding FROM message_embeddings LIMIT 1"
  ).get();
  if (!row || !row.embedding) return null;

  // Float32 = 4 bytes per dimension
  return row.embedding.byteLength / 4;
}
```

Note: sqlite-vec returns embeddings as raw bytes. A Float32Array has 4 bytes per element. Dividing byteLength by 4 gives the dimension count.

**recreateVecTable(dimensions):**
4. After recreateVecTable(1536), the message_embeddings table is empty
5. After recreateVecTable(1536), storing a 1536d embedding succeeds
6. After recreateVecTable(1536), storing a 384d embedding fails (dimension mismatch at sqlite-vec level)
7. recreateVecTable() also clears embedding_state (paired with the DROP)
8. recreateVecTable() is idempotent (calling twice with same dimension is safe)
9. recreateVecTable() works when message_embeddings does not exist yet (no error on DROP IF EXISTS)

Implementation:
```typescript
recreateVecTable(dimensions: number): void {
  this.db.exec("DROP TABLE IF EXISTS message_embeddings");
  this.db.exec(
    `CREATE VIRTUAL TABLE message_embeddings USING vec0(
      embedding float[${dimensions}]
    )`
  );
  this.db.exec("DELETE FROM embedding_state");
}
```

Note: We clear `embedding_state` here because it is logically paired -- if the vectors are gone, the state tracking must reset too. This means `clearAndReembed()` in EmbeddingService does not need to call `clearAllEmbeddings()` separately when dimensions change (the recreateVecTable already handles both).

**Test setup note:** Tests need a database with sqlite-vec loaded. The existing `embedding-repository.test.ts` already has this setup -- follow its pattern. If the existing tests create the table with `float[384]`, some new tests will need to verify behavior after `recreateVecTable(1536)`.

### Task 2: Integrate dimension-aware re-embedding into sync flow (RED-GREEN)

Wire the dimension check into the existing re-embedding flow in sync.ts so that provider/model switches with different dimensions trigger vec0 table recreation.

#### Sync command update (`src/presentation/cli/commands/sync.ts`)

**Test file:** `src/presentation/cli/commands/sync.test.ts`

Tests to write (RED phase):

**Dimension change detection in runEmbeddingPass:**
1. When model changes AND dimensions change (e.g., 384 -> 1536), `recreateVecTable()` is called with the new dimensions BEFORE `clearAndReembed()`
2. When model changes but dimensions stay the same (e.g., switching local models both at 384d), `recreateVecTable()` is NOT called -- standard `clearAndReembed()` path used
3. When no model change, `recreateVecTable()` is never called
4. When dimension change happens, user sees "Recreating embedding table for {N}-dimensional vectors..." message (unless quiet)

**The change in runEmbeddingPass():**

After the `handleModelChange()` confirmation succeeds and before `clearAndReembed()`, add dimension check:

```typescript
// After handleModelChange confirmation, before clearAndReembed
if (modelState.modelChanged && modelState.needsReEmbed) {
  // Check for dimension change
  const storedDimensions = repository.getStoredEmbeddingDimensions();
  const newDimensions = config.embedding.dimensions;

  if (storedDimensions !== null && storedDimensions !== newDimensions) {
    if (!options.quiet) {
      console.log(`Recreating embedding table for ${newDimensions}-dimensional vectors...`);
    }
    repository.recreateVecTable(newDimensions);
  }
}
```

This goes inside the existing `if (modelState.modelChanged && modelState.needsReEmbed)` block in `runEmbeddingPass()`, right after the "Clearing existing embeddings for re-embedding..." message and before the embedding pass execution.

**Test strategy for sync.test.ts:**
- The existing tests use `EmbeddingPassDeps` for DI. Add a mock repository with `getStoredEmbeddingDimensions()` and `recreateVecTable()` methods.
- Test that when `getStoredEmbeddingDimensions()` returns 384 and config has dimensions 1536, `recreateVecTable(1536)` is called.
- Test that when `getStoredEmbeddingDimensions()` returns 384 and config has dimensions 384, `recreateVecTable()` is NOT called.
- Test that when `getStoredEmbeddingDimensions()` returns null (no embeddings), `recreateVecTable()` is NOT called.

**Important:** The `EmbeddingPassDeps.repositoryOverride` is typed as `EmbeddingRepository`. The new methods must be on that class. Since Task 1 adds them to the real class, the test mocks just need to include them.
