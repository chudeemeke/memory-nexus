# Phase 29.1: Test Determinism and Environment Isolation - Research

**Researched:** 2026-03-22
**Domain:** Test isolation, dependency injection for database paths, command dispatch mocking
**Confidence:** HIGH

## Summary

The 11 failing tests share one root cause: `executeContextCommand`, `executeSearchCommand`, and `executeRelatedCommand` hardcode `getDefaultDbPath()` with no DI seam for injecting a test database. When browse dispatch tests call these functions after picker selection, they open the real user database (~266MB), do real queries against real session data, and take 30-85 seconds on Windows. The context command error handling tests have the same problem -- each test initializes the real database just to check that a nonexistent project returns exitCode 1.

The fix is straightforward: add an optional `dbPath` parameter to the options types of the affected execute functions (matching the `setTestDbPath` pattern already used in browse.ts and show.ts, but using proper DI through options rather than module-level mutation). Tests pass a temp database path; production callers omit it and get `getDefaultDbPath()` as default.

**Primary recommendation:** Add `dbPath?: string` to `ContextCommandOptions`, `SearchCommandOptions`, and `RelatedCommandOptions`. Each execute function uses `options.dbPath ?? getDefaultDbPath()`. Tests create an empty temp DB and pass its path. No module-level `setTestDbPath` mutation needed for these commands.

## Architecture Patterns

### Pattern 1: Options-based DB Path Injection

The cleanest approach given existing patterns. Already used implicitly by browse.ts (`setTestDbPath`), but the options-based approach is superior because it avoids module-level mutable state.

**What:** Add `dbPath?: string` to command options interfaces. Execute functions use `options.dbPath ?? getDefaultDbPath()`.

**Why superior to setTestDbPath pattern:**
- No module-level mutable state
- No forgotten cleanup in afterEach
- Thread-safe (parallel tests)
- Explicit per-call, not ambient

**Example:**
```typescript
export interface ContextCommandOptions {
  // ... existing fields
  /** Database path override (for testing). Defaults to getDefaultDbPath(). */
  dbPath?: string;
}

export async function executeContextCommand(
  project: string,
  options: ContextCommandOptions
): Promise<CommandResult> {
  const dbPath = options.dbPath ?? getDefaultDbPath();
  const { db } = initializeDatabase({ path: dbPath });
  // ... rest unchanged
}
```

### Pattern 2: Temp DB with Schema for Tests

Tests create a temp directory, initialize an empty database with schema, and pass its path. The `initializeDatabase()` function already handles schema creation.

```typescript
const tempDir = mkdtempSync(join(tmpdir(), "context-test-"));
const dbPath = join(tempDir, "test.db");
// initializeDatabase({ path: dbPath }) creates schema automatically
```

### Pattern 3: Browse Dispatch Isolation

Browse dispatch tests currently call real `executeSearchCommand`, `executeContextCommand`, `executeRelatedCommand` which open the real DB. Two options:

**Option A (recommended):** Once those commands accept `dbPath`, the browse command's dispatch can pass its own `dbPath` through. But browse tests already use `setTestDbPath` -- the dispatched commands need the same path.

**Option B:** Mock the dispatched execute functions entirely in browse tests. The browse tests only verify that dispatch happens (check picker was called, correct action selected). They don't need to verify the dispatched command's behavior -- that's tested in each command's own tests.

Option B is cleaner: browse tests should verify dispatch logic only, not re-test downstream commands. Mock `executeSearchCommand`, `executeContextCommand`, `executeRelatedCommand` at the module level using bun's mock system.

### Anti-Patterns to Avoid
- **Module-level setTestDbPath:** Mutable global state that requires cleanup. Existing uses in browse.ts/show.ts should be migrated to options-based injection in this phase or noted as tech debt.
- **Mocking initializeDatabase globally:** Fragile, breaks tests that need real DB behavior.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Temp DB creation | Custom DB factory | `mkdtempSync` + `initializeDatabase({ path })` | Already works, schema auto-created |
| Module mocking | Manual mock wiring | `mock.module()` from bun:test | Bun's native module mocking |

## Common Pitfalls

### Pitfall 1: Windows File Locking on Temp DB Cleanup
**What goes wrong:** SQLite WAL/SHM files keep handles open; `rmSync` fails on Windows.
**How to avoid:** `closeDatabase(db)` before cleanup. Use `{ force: true }` on rmSync. Ignore cleanup errors in afterEach (already done in browse.test.ts).

### Pitfall 2: Browse Dispatch Tests Still Hitting Real DB
**What goes wrong:** Even with dbPath on context/search/related, browse.ts dispatches to those commands without passing dbPath.
**How to avoid:** Mock the dispatched functions in browse tests rather than relying on dbPath threading.

### Pitfall 3: Forgetting to Close DB in Test Teardown
**What goes wrong:** Open DB handles prevent temp directory cleanup and can cause test flakiness.
**How to avoid:** Always close in afterEach, wrapped in try/catch.

### Pitfall 4: setTestDbPath Propagation
**What goes wrong:** browse.ts `setTestDbPath` propagates to show.ts but not to search/context/related. If browse dispatch tests aren't mocked, they still hit real DB.
**How to avoid:** Mock dispatch targets in browse tests (Pattern 3 Option B).

```typescript
export async function executeContextCommand(
  project: string,
  options: ContextCommandOptions
): Promise<CommandResult> {
  const dbPath = options.dbPath ?? getDefaultDbPath();
  const { db } = initializeDatabase({ path: dbPath });
  try {
    if (useSmartContext(options)) {
      return await executeSmartContext(db, project, options, startTime);
    }
    return await executeLegacyContext(db, project, options, startTime);
  } catch (error) {
    // ... existing error handling
  } finally {
    closeDatabase(db);
  }
}
```

### Context Error Handling Test with Temp DB
```typescript
describe("executeContextCommand error handling", () => {
  let tempDir: string;
  let dbPath: string;

  beforeEach(() => {
    tempDir = mkdtempSync(join(tmpdir(), "context-test-"));
    dbPath = join(tempDir, "test.db");
    // Initialize empty DB (schema only, no data)
    const { db } = initializeDatabase({ path: dbPath });
    closeDatabase(db);
  });

  afterEach(() => {
    try { rmSync(tempDir, { recursive: true, force: true }); } catch {}
  });

  it("sets exit code 1 when project not found", async () => {
    const result = await executeContextCommand("nonexistent", { dbPath });
    expect(result.exitCode).toBe(1);
  });
});
```

## Open Questions

1. **Should setTestDbPath be removed from browse.ts/show.ts?**
   - What we know: It works but is mutable global state
   - Recommendation: Migrate to options-based injection in this phase for consistency. Add `dbPath` to `BrowseCommandOptions` and `ShowCommandOptions` too.

2. **Programmatic API integration tests -- should they use temp DB?**
   - What we know: These tests intentionally test against real data for API contract verification
   - What's unclear: Whether the slow tests (sync, doctor) should use temp DBs
   - Recommendation: Add `dbPath` to their options but keep some tests running against real DB with explicit timeouts (already added in 28-06). For browse dispatch tests in programmatic-api.test.ts, the non-TTY check makes them fast already (exits early).
