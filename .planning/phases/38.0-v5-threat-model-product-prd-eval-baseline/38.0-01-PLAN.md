# Phase 38.0 Plan: v5 Threat Model, Product PRD, and Eval Baseline

## Objective

Create the locked foundation for v5 implementation before touching remote sync, graph, persona, ranking, dreaming, or capability interop code.

This phase exists because the current roadmap was feature-shaped, not product-readiness-shaped. The v5 implementation must start from product intent, threat model, evaluation fixtures, and requirements traceability.

## Non-Negotiable Invariants

- Do not enable public `memory remote` before the event kernel, redaction, and threat-model gates pass.
- Do not call `authkey get` or introduce raw-secret resolution through memory-nexus.
- Do not treat remote sync as a transport-only feature.
- Do not rely on old planning docs as implementation truth; verify source code.
- Do not lower the quality bar because this is first-party/private.

## Tasks

### T1 - Write v5 PRD

Create `docs/prd/2026-06-04-v5-market-leader-memory-platform.md`.

Required sections:
- Product thesis and local-first differentiation.
- Target users and use cases.
- Out-of-scope cases.
- User stories for remote sync, persona/procedural memory, temporal graph, utility ranking, dreaming, friction contract, and secure capability interop.
- Fresh-user install/configure/audit/backup/restore/upgrade flows.
- Compatibility promises for CLI JSON, exit codes, config, event schema, and data migration.
- Open decisions with owners and closure triggers.

Acceptance:
- PRD explicitly states why local-first `memory` can be excellent without authkey, hosted graph stores, or cloud LLM providers.
- PRD includes "works great without it, perfect with it" positioning for optional first-party integrations.

### T2 - Write v5 Threat Model

Create `docs/security/2026-06-04-v5-threat-model.md`.

Required sections:
- Assets: transcripts, tool output, source paths, facts, event logs, profile, graph, dreams, config, remote repos, provider keys.
- Actors: user, local agent, remote Git host, Git helper, provider, optional authkey/capability tool, malicious local process, compromised repo.
- Trust boundaries.
- Data egress paths.
- Remote sync plaintext/encryption decision matrix.
- Remote URL/ref validation policy.
- Machine identity failure policy.
- Conflict, rollback, quarantine, and recovery semantics.
- Provider egress consent and allowlist.
- Secret handling and redaction guarantees.

Acceptance:
- Every high-risk v5 phase maps to controls.
- Threat model defines what blocks implementation vs what can remain documented risk.

### T3 - Write Evaluation Baseline

Create `docs/evals/2026-06-04-v5-evaluation-baseline.md`.

Required sections:
- Eval dimensions: recall precision, recall relevance, cross-project leakage, supersedence correctness, graph traversal usefulness, persona usefulness, friction query correctness, privacy/redaction, sync recovery, dreaming safety.
- Fixture strategy: sanitized real cases plus synthetic edge cases.
- Minimum pass thresholds.
- How evals fit alongside unit/integration/coverage gates.
- Future automation path.

Acceptance:
- Each v5 feature has at least one evaluation dimension.
- The final Phase 43 review can use the eval baseline as evidence.
