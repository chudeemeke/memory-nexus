# Plan 14-02: sqlite-vec Extension Loading and Schema Migration

## Goal

Load the sqlite-vec extension alongside FTS5 in database initialization, and add the `message_embeddings` (vec0 virtual table) and `embedding_state` tracking table via schema migration. The system gracefully handles sqlite-vec being unavailable (vector tables skipped, FTS5 still works).

## must_haves

- [ ] `sqlite-vec@0.1.6` is added to package.json dependencies (pinned, no caret)
- [ ] `initializeDatabase()` attempts to load sqlite-vec AFTER FTS5 check but BEFORE schema creation
- [ ] `DatabaseInitResult` has a new `sqliteVecAvailable: boolean` field
- [ ] `createSchema()` accepts an options parameter with `sqliteVecAvailable` flag; vec0 tables only created when true
- [ ] `message_embeddings` vec0 virtual table created with `float[384]` when sqlite-vec available
- [ ] `embedding_state` regular table created with `message_id`, `embedded_at`, `model_hash` columns (always created regardless of sqlite-vec)
- [ ] When sqlite-vec is NOT available, database initialization still succeeds with `sqliteVecAvailable: false` and all FTS5 functionality works
- [ ] All existing tests continue to pass (no regressions)
- [ ] New tests cover both sqlite-vec available and unavailable paths at 95%+ coverage

## Tasks

<task id="14-02-A" title="Schema migration: add embedding tables (TDD)">

### Context

The schema is defined in `src/infrastructure/database/schema.ts` as exported `const` SQL strings appended to the `SCHEMA_SQL` array. `createSchema(db)` iterates the array and executes each statement. All DDL uses `IF NOT EXISTS` for idempotency. See the existing pattern: `SESSIONS_TABLE`, `MESSAGES_META_TABLE`, etc.

**Critical ordering from research:** sqlite-vec extension MUST be loaded before any SQL references `vec0`. The `message_embeddings` vec0 table creation MUST be conditional on sqlite-vec being available. The `embedding_state` table is regular SQL and can always be created.

### Red Phase -- Write Failing Tests

Extend `src/infrastructure/database/schema.test.ts` with new describe blocks:

1. `describe("embedding_state table")`:
   - Test `EMBEDDING_STATE_TABLE` SQL constant is defined
   - Test `createSchema(db, { sqliteVecAvailable: false })` creates the `embedding_state` table (verify via `PRAGMA table_info(embedding_state)`)
   - Test `embedding_state` has columns: `message_id` (INTEGER PRIMARY KEY), `embedded_at` (TEXT NOT NULL), `model_hash` (TEXT NOT NULL)
   - Test `embedding_state` has foreign key on `message_id` referencing `messages_meta(rowid)`
   - Test `embedding_state` has index `idx_embedding_state_model` on `model_hash`
   - Test idempotency: calling `createSchema(db, { sqliteVecAvailable: false })` twice does not error

2. `describe("message_embeddings table")`:
   - Test `MESSAGE_EMBEDDINGS_TABLE` SQL constant is defined
   - Test that when sqlite-vec IS loaded and `createSchema(db, { sqliteVecAvailable: true })` is called, the `message_embeddings` virtual table exists
   - Test that when `createSchema(db, { sqliteVecAvailable: false })` is called, no vec0 table creation is attempted (no error about missing module)

3. `describe("createSchema options parameter")`:
   - Test `createSchema(db)` with no options defaults to `{ sqliteVecAvailable: false }` (backward compatible)
   - Test `createSchema(db, { sqliteVecAvailable: true })` creates both embedding tables
   - Test `createSchema(db, { sqliteVecAvailable: false })` creates only embedding_state, not message_embeddings

**Note on sqlite-vec in tests:** For tests that need sqlite-vec, use a real `:memory:` database and call `sqliteVec.load(db)` before createSchema. If sqlite-vec is not available in the test environment, skip those specific tests with a guard: `const canLoadVec = tryLoadVec(); if (!canLoadVec) return;`

### Green Phase -- Implement

Modify `src/infrastructure/database/schema.ts`:

1. Add new exported constants:

```typescript
export const EMBEDDING_STATE_TABLE = `
CREATE TABLE IF NOT EXISTS embedding_state (
  message_id INTEGER PRIMARY KEY,
  embedded_at TEXT NOT NULL,
  model_hash TEXT NOT NULL,
  FOREIGN KEY (message_id) REFERENCES messages_meta(rowid) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_embedding_state_model ON embedding_state(model_hash);
`;

export const MESSAGE_EMBEDDINGS_TABLE = `
CREATE VIRTUAL TABLE IF NOT EXISTS message_embeddings USING vec0(
  embedding float[384]
);
`;
```

3. Add `SchemaOptions` interface: `{ sqliteVecAvailable?: boolean }`

   - After iterating `SCHEMA_SQL`, check `options?.sqliteVecAvailable`
   - If true, execute `MESSAGE_EMBEDDINGS_TABLE` SQL
   - Default: `sqliteVecAvailable = false` (backward compatible with all existing callers)

Update `src/infrastructure/database/index.ts`:
- Add exports for `EMBEDDING_STATE_TABLE`, `MESSAGE_EMBEDDINGS_TABLE`
- Add `type SchemaOptions` to createSchema export (update signature)

<task id="14-02-B" title="sqlite-vec extension loading in connection.ts (TDD)">

### Context

`initializeDatabase()` in `connection.ts` is synchronous. It currently: creates Database, enables foreign keys, configures WAL, sets pragmas, checks FTS5, runs quick_check, applies schema. The sqlite-vec extension must load AFTER FTS5 check and BEFORE schema application.

**Research finding (Open Question 3):** `initializeDatabase()` stays synchronous. Import `sqlite-vec` at the top of connection.ts (the package is lightweight -- just native extension path resolution). The heavy ONNX runtime import stays dynamic in the provider (Plan 14-03).

**Research finding (Pitfall 1):** sqlite-vec MUST load before schema creation or `CREATE VIRTUAL TABLE ... USING vec0(...)` will fail with "no such module: vec0".

### Red Phase -- Write Failing Tests

Extend `src/infrastructure/database/connection.test.ts`:

1. `describe("sqlite-vec extension loading")`:
   - Test `initializeDatabase({ path: ":memory:" })` returns `DatabaseInitResult` with `sqliteVecAvailable` field (boolean)
   - Test that when sqlite-vec loads successfully, `sqliteVecAvailable` is `true` and `SELECT vec_version()` works
   - Test that when sqlite-vec fails to load (simulate by mocking), `sqliteVecAvailable` is `false` and database still initializes with FTS5 working
   - Test that `message_embeddings` table exists when `sqliteVecAvailable` is `true`
   - Test that `embedding_state` table exists regardless of `sqliteVecAvailable` value
   - Test that existing schema tables (sessions, messages_meta, etc.) are unaffected

2. `describe("backward compatibility")`:
   - Test existing tests that call `initializeDatabase()` continue to work (the new field is additive)

**Mocking sqlite-vec failures:** To test the unavailable path, use a try/catch wrapper or a test-specific flag. One approach: create a helper `loadSqliteVec(db)` function that can be overridden in tests. Another approach: test both paths using integration tests -- one with real sqlite-vec (if available), one verifying the graceful fallback by checking the returned `sqliteVecAvailable` field.

### Green Phase -- Implement

Install dependency:
```bash
bun add sqlite-vec@0.1.6
```

Modify `src/infrastructure/database/connection.ts`:

1. Add import at top (sqlite-vec is lightweight):
```typescript
import * as sqliteVec from "sqlite-vec";
```

**WAIT -- Research Open Question 3 recommends top-level import, but this makes testing harder.** Better approach: use a function that wraps the import, testable via dependency injection:

```typescript
/**
 * Attempt to load sqlite-vec extension into the database.
 *
 * @param db Database instance to load the extension into
 * @returns true if loaded successfully, false otherwise
 */
function loadSqliteVecExtension(db: Database): boolean {
  try {
    const sqliteVec = require("sqlite-vec");
    sqliteVec.load(db);
    return true;
  } catch {
    // sqlite-vec not available -- vector search will be disabled
    return false;
  }
}
```

Actually, use dynamic require (not import) since `initializeDatabase` is synchronous. Bun supports `require()` for this. Alternatively, wrap in try/catch:

```typescript
function loadSqliteVecExtension(db: Database): boolean {
  try {
    // eslint-disable-next-line @typescript-eslint/no-require-imports
    const sqliteVec = require("sqlite-vec");
    sqliteVec.load(db);
    return true;
  } catch {
    return false;
  }
}
```

2. Update `initializeDatabase()`:
   - After FTS5 check, before schema application:
   ```typescript
   // Load sqlite-vec extension (optional -- vector search disabled if unavailable)
   const sqliteVecAvailable = loadSqliteVecExtension(db);
   ```
   - Pass to schema creation:
   ```typescript
   if (applySchema) {
     createSchema(db, { sqliteVecAvailable });
   }
   ```

3. Update `DatabaseInitResult` interface:
```typescript
export interface DatabaseInitResult {
  db: Database;
  walEnabled: boolean;
  fts5Available: boolean;
  sqliteVecAvailable: boolean;  // NEW
}
```

4. Update return statement to include `sqliteVecAvailable`.

5. Export `loadSqliteVecExtension` for testing (or make it a module-level function that tests can verify via the result).
