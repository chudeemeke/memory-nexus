# Plan 16.1-01: Size-Aware Migration Conflict Resolution with WAL/SHM Cleanup and Pending Guard

## Goal

Fix the race condition where `migrateFromLegacy()` does not handle the partial migration state correctly. When both legacy `~/.memory-nexus/memory.db` (266MB of real data) and XDG `~/.local/share/memory/memory.db` (221KB empty stub) exist, migration must compare file sizes and keep the larger database. Additionally, stale WAL/SHM sidecar files at the destination must be cleaned up before overwriting to prevent database corruption.

**Root cause:** The move loop in `migrateFromLegacy()` skips items that do not exist at the source (`!existsSync(item.source)`), but never checks whether the destination already exists. When a prior CLI invocation created an empty XDG database via `initializeDatabase()`, subsequent migration calls encounter a "partial" state where both paths have data. The `moveFileOrDir()` function uses `renameSync` which silently overwrites on POSIX, but the code provides no guardrails: it could overwrite a populated database with an empty one (if someone ran `memory sync` on the XDG path first and then tried to migrate), or overwrite an empty stub with real data (the intended outcome that happens to work on POSIX but fails silently on Windows if the file is locked).

**Research recommendations followed:** Option A (fix migration to handle partial state correctly) is the primary fix. Additionally, belt-and-suspenders defense per SC3: `isMigrationPending()` is exported from `migration.ts` and called by `index.ts` before any command action can trigger `initializeDatabase()`. This prevents empty stub creation in the first place. No coupling of migration into connection.ts -- the guard lives at the CLI entry point level only.

## must_haves

- [ ] When destination file exists and is SMALLER than source file, migration overwrites destination with source (legacy DB replaces empty stub)
- [ ] When destination file exists and is LARGER OR EQUAL to source file, migration keeps destination and removes legacy copy (XDG DB with new data preserved)
- [ ] Before overwriting a destination `.db` file, WAL (`.db-wal`) and SHM (`.db-shm`) sidecar files at destination are deleted to prevent corruption
- [ ] When destination directory exists (logs, hooks, backups), migration skips the directory move (does not merge)
- [ ] After size-aware resolution, legacy source files that were superseded (dest >= source) are removed from legacy dir
- [ ] Migration is idempotent: running it twice produces the same result
- [ ] Legacy directory is cleaned up (removed) after all items handled, if empty
- [ ] `isMigrationPending()` exported from migration.ts returns true when legacy DB exists with more data than XDG DB (or XDG DB does not exist)
- [ ] CLI entry point (`index.ts`) calls `isMigrationPending()` -- if true, runs `migrateFromLegacy()` before `program.parse()`; if false, skips migration entirely (performance optimization)
- [ ] `isMigrationPending()` does NOT import into connection.ts -- guard is at CLI entry point only
- [ ] All existing migration tests continue to pass (no regressions)
- [ ] New tests cover: partial state with empty stub at destination, partial state with larger DB at destination, WAL/SHM cleanup, directory skip behavior, isMigrationPending() states
- [ ] 95%+ coverage at EACH metric for migration.ts

### Context

### Green Phase -- Implement

1. **Add `cleanupDatabaseSidecars()` helper** in `migration.ts`:

   ```typescript
   /**
    * Remove WAL and SHM sidecar files for a database.
    *
    * SQLite WAL mode creates .db-wal and .db-shm files alongside the main
    * database. When replacing the main file, stale sidecars must be removed
    * to prevent the new database from inheriting old WAL state (corruption).
    *
    * @param dbPath Path to the main .db file
    */
   function cleanupDatabaseSidecars(dbPath: string): void {
       for (const suffix of ["-wal", "-shm"]) {
           const sidecarPath = dbPath + suffix;
           if (existsSync(sidecarPath)) {
               unlinkSync(sidecarPath);
           }
       }
   }
   ```

   This is a private helper (not exported). It only removes the WAL/SHM files, NOT the main DB file. The main DB file is either overwritten by `moveFileOrDir()` or left intact.

2. **Add `isMigrationPending()` exported function** in `migration.ts`:

   Place this after the existing `getMigrationStatus()` function, before `migrateFromLegacy()`.

   ```typescript
   /**
    * Check whether a legacy database needs migration to XDG paths.
    *
    * Returns true when the legacy ~/.memory-nexus/memory.db exists AND either:
    *   (a) no XDG database exists yet, OR
    *   (b) the legacy database is larger than the XDG database (empty stub).
    *
    * This is a lightweight check for the CLI entry point to decide whether
    * to run migrateFromLegacy() before any command action can create an
    * empty database via initializeDatabase().
    *
    * ORDERING CONTRACT: The CLI entry point (index.ts) must call this
    * function and, if true, call migrateFromLegacy() BEFORE program.parse()
    * dispatches to any command that calls initializeDatabase(). This
    * prevents the empty-stub race condition where initializeDatabase()
    * creates a 221KB empty database before migration can move the real
    * 266MB legacy database into place.
    *
    * This function does NOT import from connection.ts. The guard lives
    * at the presentation layer (index.ts), not the infrastructure layer
    * (connection.ts), to avoid coupling between independent modules.
    */
   export function isMigrationPending(): boolean {
       const legacyDir = getLegacyDir();
       if (!existsSync(legacyDir)) {
           return false;
       }

       const legacyDbPath = join(legacyDir, "memory.db");
       if (!existsSync(legacyDbPath)) {
           return false;
       }

       const xdgDbPath = getDbPath();
       if (!existsSync(xdgDbPath)) {
           return true; // Legacy DB exists, XDG does not -- migration needed
       }

       // Both exist: migration needed only if legacy is larger (XDG is an empty stub)
       const legacySize = statSync(legacyDbPath).size;
       const xdgSize = statSync(xdgDbPath).size;
       return legacySize > xdgSize;
   }
   ```

   **Key details:**
   - Uses `getLegacyDir()` which already exists in migration.ts (the `homedir() + "/.memory-nexus"` helper)
   - Uses `getDbPath()` which is already imported from paths.ts
   - All operations are sync (`existsSync`, `statSync`) -- no async
   - Returns `false` when sizes are equal (destination is kept per size-aware resolution)
   - Does NOT call `migrateFromLegacy()` itself -- just reports the state

3. **Add destination-exists handling** in the move loop of `migrateFromLegacy()`:

   Insert the destination check between the `!existsSync(item.source)` early return and the `moveFileOrDir()` call:

   ```typescript
   for (const item of moveList) {
       if (!existsSync(item.source)) {
           continue;
       }

       // Handle destination already exists (partial migration state)
       if (existsSync(item.dest)) {
           if (item.isDir) {
               // Directories: skip when destination already exists.
               // Logs, hooks, backups are not critical enough to merge.
               continue;
           }

           // Files: compare sizes to determine which to keep
           const sourceSize = statSync(item.source).size;
           const destSize = statSync(item.dest).size;

           if (destSize >= sourceSize) {
               // Destination has equal or more data; keep it, remove legacy copy
               unlinkSync(item.source);
               itemsMoved.push(item.name);
               continue;
           }

           // Source is larger: clean up destination sidecar files before overwrite
           // (prevents stale WAL/SHM from corrupting the migrated database)
           if (item.dest.endsWith(".db")) {
               cleanupDatabaseSidecars(item.dest);
           }
           // Fall through to normal moveFileOrDir() which overwrites destination
       }

       try {
           moveFileOrDir(item.source, item.dest, item.isDir);
           completedMoves.push({ item, rolledBack: false });
           itemsMoved.push(item.name);
       } catch (error) {
           // ... existing rollback logic unchanged ...
       }
   }
   ```

   **Critical detail:** When `destSize >= sourceSize`, we `unlinkSync(item.source)` to clean up the legacy copy and add the item name to `itemsMoved` so the migration knows something was handled. This ensures the legacy directory can be cleaned up at the end. We do NOT add to `completedMoves` because there is nothing to roll back (the destination was not modified).

   **Critical detail:** The WAL/SHM cleanup is guarded by `.endsWith(".db")` rather than checking `item.name === "memory.db"`. This future-proofs the logic for any database file, though currently only `memory.db` exists.

   **Critical detail:** After cleanup, the code falls through to `moveFileOrDir()`. The `renameSync` inside `moveFileOrDir()` will overwrite the destination file atomically. On EXDEV fallback, `copyFileSync` also overwrites by default. The destination `.db` file does NOT need to be deleted before the move -- `renameSync` and `copyFileSync` handle overwrites. Only the sidecars need explicit removal.

4. **Verify the rollback logic still works correctly:**

   The rollback loop iterates `completedMoves` in reverse. Items resolved via the size comparison (dest >= source) are NOT added to `completedMoves`, so they are not rolled back. This is correct: rolling back would mean restoring a file we already deleted from legacy, but the destination was never modified, so no rollback is needed.

   Items resolved via overwrite (source > dest) ARE added to `completedMoves` via the normal `moveFileOrDir()` path. If a subsequent move fails and triggers rollback, the overwritten destination DB would be moved back to legacy. This loses the WAL/SHM cleanup, but since rollback means the entire migration failed, the user will re-attempt later.

5. **Wire `isMigrationPending()` into the CLI entry point** in `src/presentation/cli/index.ts`:

   Update the import statement to also import `isMigrationPending`:

   ```typescript
   import { migrateFromLegacy, isMigrationPending } from "../../infrastructure/migration.js";
   ```

   Update the `if (import.meta.main)` block:

   ```typescript
   // Run if executed directly
   if (import.meta.main) {
     // ORDERING CONTRACT: migration MUST complete before program.parse()
     // dispatches to any command action that calls initializeDatabase().
     // isMigrationPending() is a lightweight check that avoids running
     // the full migration logic on every invocation when no legacy data exists.
     if (isMigrationPending()) {
       migrateFromLegacy();
     }
     program.parse();
   }
   ```

   **Key details:**
   - `isMigrationPending()` is a fast-path optimization: when no legacy dir exists, it returns false with a single `existsSync` call, avoiding the full `migrateFromLegacy()` cost on every invocation.
   - When it returns true, `migrateFromLegacy()` runs synchronously before `program.parse()`, guaranteeing the XDG database is populated with real data before any command action can call `initializeDatabase()`.
   - This satisfies SC3: `initializeDatabase()` cannot create an empty stub when migration is pending because migration always runs first. The guard is at the entry point, not inside `initializeDatabase()` itself.
