# Phase 16.1: Migration Race Condition Fix - Research

**Researched:** 2026-02-27
**Domain:** Database migration, filesystem operations, startup sequencing
**Confidence:** HIGH

## Summary

Phase 16 human verification revealed a race condition in the CLI startup sequence. When a user has a legacy database at `~/.memory-nexus/memory.db` (266MB of real data), the first invocation of any `memory` command after installing v2.0 proceeds as follows:

1. `migrateFromLegacy()` is called at `src/presentation/cli/index.ts:84` -- but the current implementation only checks whether `~/.memory-nexus/` exists. It does NOT check whether the destination already has data.
2. The Commander action for the subcommand then calls `initializeDatabase({ path: getDefaultDbPath() })` which resolves to `~/.local/share/memory/memory.db`. The `initializeDatabase` function calls `mkdirSync(dirname(path), { recursive: true })` at `connection.ts:124` and then `new Database(path, { create: true })` at `connection.ts:138`. This creates an empty 221KB database with schema but zero session data.
3. Because the XDG data directory now exists after step 2, `getMigrationStatus()` returns `"partial"` on subsequent runs (both legacy and new paths exist), and `migrateFromLegacy()` creates its target directories but then tries to `renameSync` the legacy `memory.db` onto the XDG `memory.db` -- this succeeds on the same filesystem (overwrites destination), but the race is whether the empty stub was already created first.

The actual failure mode observed: `migrateFromLegacy()` ran first (line 84), successfully moved the legacy DB to XDG path. But then `initializeDatabase()` was called by the command action and opened the file at XDG path -- which now has real data. This path works. The problem is the **opposite scenario**: when some prior command already created the empty XDG DB (e.g., the user previously ran `memory doctor` which calls `initializeDatabase` via the health checker), `migrateFromLegacy()` sees `newExists=true` from `getMigrationStatus()`, returns status `"partial"`, but still proceeds to move files. However, `moveFileOrDir` uses `renameSync` which overwrites the destination on POSIX systems but may fail on Windows if the file is locked. More critically, the `migrateFromLegacy()` function does NOT currently handle the `"partial"` case -- it just checks `!existsSync(legacyDir)` and proceeds to move everything, potentially overwriting a DB that has been used for new syncs.

The fix requires defense-in-depth at multiple levels:

**Primary recommendation:** Fix the startup ordering so `migrateFromLegacy()` runs before any database initialization, and add a size comparison guard in the migration logic to always prefer the larger database when both paths contain data.

### Pattern 1: Size-Aware Migration Conflict Resolution

**What:** When both legacy and XDG databases exist (partial migration), compare file sizes and keep the larger one.
**When to use:** The `migrateFromLegacy()` function encounters an existing file at the destination path.
**Confidence:** HIGH -- this is the core fix.

```typescript
// In migration.ts, inside the file move loop
// Before moving memory.db, check if destination already exists
if (existsSync(item.dest) && item.name === "memory.db") {
    const sourceSize = statSync(item.source).size;
    const destSize = statSync(item.dest).size;

    if (destSize >= sourceSize) {
        // Destination has more data (or equal); skip the move, keep destination
        // This handles the case where the user already synced to the new path
        continue;
    }
    // Source is larger: overwrite the empty stub at destination
    // (the normal move path handles this)
}
```

### Pattern 2: Migration-Before-Init Guard

**What:** The CLI entry point must guarantee migration completes before any command action can call `initializeDatabase()`.
**When to use:** Already the intended design (line 84 of index.ts calls `migrateFromLegacy()` before `program.parse()`), but needs verification that no other path bypasses this.
**Confidence:** HIGH -- the current ordering is correct for the main entry point.

The current code at `src/presentation/cli/index.ts:83-86`:
```typescript
if (import.meta.main) {
  migrateFromLegacy();
  program.parse();
}
```

This ordering is already correct: `migrateFromLegacy()` is synchronous and runs before `program.parse()` dispatches to any command action. The race condition is not in the ordering of these two calls within a single invocation. It is in the scenario where a **prior invocation** already created the empty XDG database (e.g., via `memory doctor`, `memory sync`, etc.), and then a subsequent invocation calls `migrateFromLegacy()` which encounters the `"partial"` state.

### Pattern 3: isMigrationPending Guard for initializeDatabase

**What:** Add an optional pre-check so `initializeDatabase()` can be told not to create a new database when migration is pending.
**When to use:** Defense-in-depth. Even if migration handles the partial case correctly, this prevents creating empty stubs in the first place.
**Confidence:** MEDIUM -- this is secondary protection. The primary fix is in migration.ts.

There are two options for this guard:

**Option A (Simpler):** No guard in `initializeDatabase()` at all. Just fix migration to handle the partial case correctly. This is sufficient because the entry point guarantees migration runs first within any single process invocation.

**Option B (Defense-in-depth):** Add an `isMigrationPending()` check that returns true when `~/.memory-nexus/memory.db` exists and the XDG `memory.db` does not (or is smaller). `initializeDatabase()` could refuse to create a new DB file when this returns true. However, this couples connection.ts to migration.ts, which violates the current separation.

**Recommendation:** Option A. The migration module should handle all states correctly (pending, partial, complete). Adding guards in `initializeDatabase()` creates coupling between two independent modules. The success criteria mentions `isMigrationPending()` in `initializeDatabase()`, but the simpler and cleaner approach is making migration handle partial state properly and ensuring the startup sequence is deterministic.

If the user explicitly wants Option B for belt-and-suspenders safety, it can be implemented as a standalone function in `migration.ts` (exported, not coupled into connection.ts) that the CLI entry point calls before any DB init.

### Anti-Patterns to Avoid

- **Opening two database connections simultaneously:** Do not open both legacy and XDG databases to compare row counts. File size comparison is sufficient and avoids lock contention.
- **Deleting the destination before moving:** Never delete the existing XDG database before confirming the legacy source is larger. Always compare first, then overwrite atomically via `renameSync`.
- **Making initializeDatabase depend on migration module:** This creates a circular dependency risk (migration imports `getDbPath` from paths, connection imports from migration). Keep the modules independent.
- **Async migration:** The current migration is synchronous. Do not make it async -- this changes the contract at the CLI entry point and every test.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Atomic file replacement | Custom lock-based replacement | `renameSync` (POSIX) or copy-then-rename | `renameSync` is atomic on same filesystem; already used |
| Database size detection | Open DB and count rows | `statSync(path).size` | File size is 1000x cheaper than opening+querying; 221KB vs 266MB is unambiguous |

**Key insight:** The existing `moveFileOrDir()` function already handles the actual move (including EXDEV fallback). The fix is about deciding WHEN to move, not HOW.

## Common Pitfalls

### Pitfall 1: Windows File Locking

**What goes wrong:** On Windows, `renameSync` may fail if the destination file is held open by another process (e.g., a prior `memory` invocation that did not cleanly close the database).
**Why it happens:** Windows uses mandatory file locking; POSIX uses advisory locking.
**How to avoid:** The existing `closeDatabase()` function switches from WAL to DELETE journal mode before closing, which removes WAL/SHM files. Ensure the destination DB is not open before attempting the overwrite. In the migration path, no DB connection is open yet (migration runs before `program.parse()`), so this should not be an issue.
**Warning signs:** `EPERM` or `EBUSY` errors during `renameSync` on Windows.

### Pitfall 2: WAL/SHM Files at Destination

**What goes wrong:** If the empty XDG database was opened in WAL mode (it was -- `initializeDatabase` enables WAL), there may be `.db-wal` and `.db-shm` files alongside it. `renameSync` only replaces the main `.db` file; the stale WAL/SHM files could corrupt the migrated database.
**Why it happens:** WAL files reference specific database state. After replacing the main file, stale WAL files cause SQLite to apply old transactions to the new database.
**How to avoid:** When overwriting an existing destination database during migration, also delete any `.db-wal` and `.db-shm` files at the destination before the move. This is critical.
**Warning signs:** "database disk image is malformed" errors after migration.

### Pitfall 3: EXDEV (Cross-Device) During Overwrite

**What goes wrong:** If legacy path (`~/.memory-nexus/`) and XDG path (`~/.local/share/memory/`) are on different filesystems (e.g., different mount points on Linux), `renameSync` fails with EXDEV.
**Why it happens:** `rename(2)` cannot cross filesystem boundaries.
**How to avoid:** Already handled by `moveFileOrDir()` which falls back to copy+delete on EXDEV. But the overwrite scenario (destination exists) needs special handling: delete the destination first, then do the copy+delete. The current `moveFileOrDir()` does not delete the destination before copying -- `copyFileSync` overwrites by default for files, but `cpSync` for directories may merge rather than replace.
**Warning signs:** `EXDEV` error code from `renameSync`.

### Pitfall 4: Idempotency After Successful Migration

**What goes wrong:** Running migration twice should produce the same result. After the first successful migration, the legacy directory is removed. A second call should be a no-op.
**Why it happens:** Already handled -- `migrateFromLegacy()` returns early when `!existsSync(legacyDir)`.
**How to avoid:** No action needed for this case; it already works.
**Warning signs:** None -- already idempotent for the clean case.

### Pitfall 5: Partial State After Power Failure

**What goes wrong:** If migration is interrupted between moving files (e.g., DB moved but config not yet moved), subsequent runs see `"partial"` state.
**Why it happens:** Files are moved sequentially; no transaction wrapping.
**How to avoid:** The existing rollback logic handles forward failures. For the partial state (prior interruption), the fix should detect which specific files need moving and handle each independently. The current code already skips items that don't exist at the source (`if (!existsSync(item.source)) continue`), so partial recovery already works for most cases. The new fix just needs to also handle the case where the source exists AND the destination exists.

### Fix: Add Destination-Exists Check with Size Comparison

```typescript
// Proposed addition inside the move loop in migration.ts
for (const item of moveList) {
    if (!existsSync(item.source)) {
        continue;
    }

    // Handle destination already exists (partial migration)
    if (existsSync(item.dest)) {
        if (!item.isDir) {
            const sourceSize = statSync(item.source).size;
            const destSize = statSync(item.dest).size;
            if (destSize >= sourceSize) {
                // Destination has equal or more data; keep it, remove legacy copy
                unlinkSync(item.source);
                itemsMoved.push(item.name);  // Track as "handled"
                continue;
            }
            // Source is larger: clean up destination (including WAL/SHM) before move
            cleanupDatabaseFiles(item.dest);
        } else {
            // For directories, skip if destination already exists
            // (logs, hooks, backups -- not critical enough to merge)
            continue;
        }
    }

    try {
        moveFileOrDir(item.source, item.dest, item.isDir);
        completedMoves.push({ item, rolledBack: false });
        itemsMoved.push(item.name);
    } catch (error) {
        // existing rollback logic
    }
}
```

### Fix: WAL/SHM Cleanup Helper

```typescript
// Proposed helper in migration.ts
function cleanupDatabaseFiles(dbPath: string): void {
    // Remove WAL and SHM files that would be stale after DB replacement
    for (const suffix of ["-wal", "-shm"]) {
        const sidecarPath = dbPath + suffix;
        if (existsSync(sidecarPath)) {
            unlinkSync(sidecarPath);
        }
    }
    // Remove the main DB file to allow clean rename
    unlinkSync(dbPath);
}
```

## Open Questions

1. **Directory merge behavior for partial migration**
   - What we know: For files (memory.db, config.json), size comparison works cleanly. For directories (logs, hooks, backups), the behavior when both source and destination exist is less clear.
   - What's unclear: Should we merge directory contents, or skip the directory move if destination exists?
   - Recommendation: Skip directory moves when destination exists (logs are not critical data; hooks are re-installed by migration). This keeps the logic simple. The important thing is preserving the database.

2. **Should `getMigrationStatus()` be enhanced to detect the empty-stub scenario?**
   - What we know: Currently returns `"partial"` for any case where both paths have data. A new status like `"stale-destination"` could distinguish empty stub from real data at destination.
   - What's unclear: Whether any consumer of `MigrationStatus` needs this distinction.
   - Recommendation: No. The migration function itself handles the distinction via file size comparison. Adding more status values adds complexity without consumer benefit. The doctor command can use the existing `"partial"` status and file size info if needed.
