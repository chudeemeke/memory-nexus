**FrictionService (src/application/services/friction-service.ts):**

Constructor injection of IFrictionRepository. Service enforces business rules and delegates to repository.

Methods:

- **log(params: { description, severity?, category?, context?, sourceProject? }):** Create FrictionEntry with status "open", loggedAt = new Date(), severity defaults to "medium", category defaults to "cli". Call repository.save(). Return saved entry.

- **resolve(id: number, resolution: string):** Verify entry exists via findById. If not found, throw MemoryError with ErrorCode.NOT_FOUND. If already resolved/wont-fix, throw MemoryError with appropriate message. Call repository.resolve(id, resolution).

Actually, looking again at the CONTEXT.md -- resolve() sets resolution and resolvedAt. updateStatus() only sets status. **Decision:** Use the repository's resolve() method for the "resolved" path. **executeFrictionCommand(options):**

Follow the executeStatsCommand pattern exactly:
1. Initialize database (initializeDatabase + createSchema)
2. Create SqliteFrictionRepository(db)
3. Create FrictionService(repository)
4. Dispatch based on options.action
5. Format output (text or JSON)
6. Close database
7. Return { exitCode: 0 } on success

For text output formatting:
- log: "Logged friction #42 (high/search)"
- list: Table format with id, severity, category, description (truncated to 60 chars), age
- resolve: "Resolved friction #42"
- wont-fix: "Marked friction #42 as won't fix"
- dashboard: Basic stats output (placeholder for Plan 03)

For JSON output: Return the domain objects serialized as JSON.

Error handling: Wrap in try/catch, return { exitCode: 1 } on error. Use formatError/formatErrorJson from existing formatters.

**CRITICAL: Define --json on EACH subcommand individually, not on the parent friction command.** Commander.js does not inherit options from parent to child (Pitfall 1 from research).
